Resource management and architecture policies

On this page 5 sections
  1. Resource Saver modes
  2. Engine budgets
  3. Apple Silicon and amd64

Resource Saver is opt-in and disabled by default. Its host-side HTTP listeners remain available while eligible applications are asleep. An initiating request waits for the owned task and its readiness checks before the original method, headers and body are forwarded.

Resource Saver modes#

ModeWhat changesWhat remains
disabledNo new automatic suspensionExisting owned sleepers retain their wake listeners
engine-idle-suspendStops only a verified, wholly idle Porto-owned Lima engineVM disk, configuration, and host listeners
container-pauseFreezes eligible tasks, reducing their process CPUResident process memory and disk data
container-scale-to-zeroStops eligible tasks, releasing task memoryContainer metadata, writable layers, volumes and host listeners; process memory is lost

Configure global policy in Settings or with:

porto resource-saver configure --mode container-scale-to-zero --idle 300 --wake 60
porto resource-saver container example-api --mode stop
porto resource-saver status

The container inspector also exposes pause, stop and exclusion choices. Mounted or stateful workloads require separate explicit consent (--stateful in the container command). Opting in does not make unsupported workloads eligible.

Equivalent container/Compose labels are dev.porto.resource-saver=pause or stop, dev.porto.resource-saver.stateful=true for mounted data, and an optional dev.porto.resource-saver.idle-seconds. The existing dev.porto.http-port and dev.porto.hostname labels provide the owned HTTP route. Every Compose member must opt in, and non-HTTP dependencies need health checks. The application is resumed as one group.

Settings and configure --exclude 'database-*,important-api' support name exclusions. Per-application overrides use IDs such as compose:example or container:<full-ID> and JSON fields mode and idleSeconds:

porto resource-saver configure --overrides '{"compose:example":{"idleSeconds":900}}'

Safety and request boundaries#

Only HTTP/HTTPS requests through Porto's URL wake listeners are retained. Published ports used directly, raw TCP/UDP and additional published protocols do not provide first-connection wake. The bounded queue defaults to 64 requests, 16 MiB per body, and a 60-second wake/readiness deadline. Client cancellation releases its reservation; concurrent requests share one resume. Active proxied streams and WebSocket upgrades hold the application active until disconnect. Wake queue and body limits apply only to requests waiting for an owned sleeper. Readiness releases the queue reservation while retaining the activity lease; ordinary traffic to an already-running application is not capped by wake limits. Queued upload bodies are staged in private temporary files within those limits before readiness wait. This lets HTTP/1 detect a disconnected uploading client promptly instead of retaining its wake until timeout. The wake deadline also bounds upload staging; temporary data is removed on completion, cancellation or failure. Already-running applications keep their ordinary streaming behavior.

Interactive containers, running execs, unobservable multi-process applications, established connections, unsupported networks, unmanaged dependencies, missing metrics, incomplete inventory and ambiguous routes block automatic suspension. Idle detection uses observed CPU, network and disk activity, not a VM's reserved memory. Long-lived internal connections also conservatively count as activity.

Engine suspension additionally checks every containerd namespace and active BuildKit work. Running or manually paused tasks, Kubernetes nodes, native file attachments, data operations and incomplete observations prevent it. External containerd installations and native Windows containers are not automatically suspended.

Ownership is identity-bound and journaled before transitions, then verified against backend metadata before resume. A manual lifecycle action releases only that selected member from automatic ownership. Pause ownership is quarantined after daemon downtime because an external manual unpause/re-pause cannot be proven from a saved PID alone; resume it manually before opting in again. Stopped-task ownership is checked again on wake. Failed wakes return a gateway error with diagnostics, never a successful empty response. Backend pause, suspension, resume and failure events appear in Activity.

Compose readiness uses the configured probe rather than merely a running PID. Exec-form health checks retain their original argument array, without adding a shell requirement to scratch images. Porto schedules probes for its explicitly managed workloads and health configurations, including compatibility-created containers, without adopting their filesystem or CNI lifecycle. Before the first probe, Docker inspection reports starting, not a missing healthcheck.

Engine budgets#

CPU, memory, swap and disk settings apply only to Porto's owned Lima engine. Use Settings or:

porto docker engine-resources configure --cpus 2 --memory 4096 --swap 0 --disk 100
porto docker engine-resources apply --restart-engine
porto docker engine-resources status

CPU, memory and disk zeroes preserve existing settings or the provider's defaults for a new engine. Omitted swap leaves it unchanged; swap zero disables only Porto-owned swap. Managed swap uses an owned Linux swap file and refuses unmanaged swap or unsupported filesystems. Other guest provisions are preserved.

Existing engines require an explicit idle restart. Disk capacity may only grow; shrinking or changing an unsupported driver is rejected before configuration mutation. Failed edits restore the original configuration and preserve the existing VM disk. Disk growth is not an undoable shrink operation.

Apple Silicon and amd64#

Architecture policy is separate from Resource Saver:

porto runtime acceleration status
porto runtime acceleration configure --policy rosetta-preferred --rosetta
porto runtime acceleration apply --restart-engine

automatic uses verified backend capabilities. native-only rejects foreign platforms, including BuildKit solve constraints. rosetta-preferred uses a configured Rosetta handler, with a verified QEMU fallback when unavailable. qemu-compatible requires the QEMU path. Container inspector creation options, the dev.porto.architecture-policy Compose/container label, and the VM --architecture-policy option override global policy for that workload.

Porto probes Apple's Virtualization.framework directly, Lima's installed drivers and guest agents, matching QEMU executables, and guest binfmt handlers. Container handlers must be enabled, executable and carry the fix-binary flag. Capabilities are refreshed rather than retained across provider upgrades. Native arm64 workloads remain native; creating one does not install emulation software. Existing owned-engine QEMU setup remains scoped to that guest.

Rosetta is opt-in, requires Apple Silicon, an arm64 VZ guest and an already installed Apple runtime. If needed, explicitly run softwareupdate --install-rosetta and accept Apple's license yourself. Porto does not silently install it or register host-wide emulation handlers. QEMU-backed engines cannot be converted to VZ or have their disks replaced. After a VZ engine has a Rosetta filesystem device, disabling translation keeps that existing device configuration and disables only its binfmt handler. Selecting QEMU does not remove a guest device or change the VM's architecture.

For a native arm64 standalone VM with optional amd64 userspace:

porto vm create example --image ubuntu-24.04 --vm-type vz --arch aarch64 --rosetta

An amd64 kernel on Apple Silicon requires QEMU full-system software emulation, not Rosetta or hardware-accelerated amd64 virtualization. The matching QEMU executable and additional Lima Linux guest agent must be available. Apple Silicon desktop bundles include the extra guest agent; source installs may need lima-additional-guestagents. Snapshots retain their QEMU-only boundary. The dashboard and runtime status distinguish native, Rosetta, QEMU and unsupported/missing-capability states without claiming unmeasured speedups.

Standalone VM acceptance is separate from container-engine acceptance. On a supported Apple Silicon host, the following command authorizes two disposable standalone VMs, with no host mounts and 2 GiB RAM each. They run sequentially: the first uses an arm64 VZ kernel with real amd64 Rosetta userspace and native arm64 ELF execution; the second boots an actual amd64 kernel under QEMU. Both verify persistent guest-home data across stop/start and remove only their own instances afterward:

PATH="$PWD/stage/runtime-darwin-arm64/bin:$PWD/stage/runtime-darwin-arm64/lima/bin:$PATH" \
  PORTO_TEST_NATIVE_STANDALONE_POLICIES=1 \
  go test ./internal/vm -run '^TestNativeStandaloneArchitecturePolicies$' \
    -count=1 -timeout=50m -v

Optimized synchronized project shares#

macOS and Linux can opt selected, registered project roots into a maintained Mutagen two-way-safe session. Windows/WSL retains ordinary bind mounts and the existing selected-distribution integration; synchronized mode is capability gated rather than substituting different path or ownership semantics.

porto shares create example-project --ignore node_modules,dist
porto shares status
porto shares mode <share-id> bind
porto shares mode <share-id> synchronized
porto shares detach <share-id> --confirm

Settings exposes the same project selector, startup/scan/staging state, connectivity, conflicts and filesystem problems. Only the selected root is synchronized into its identity-bound /mnt/porto-sync/<share-id> directory. Whole home directories, filesystem roots, overlapping roots and symlink roots are rejected. No existing host directory or guest copy is deleted on detach.

New container bind mounts inside a selected synchronized root use that guest copy after a successful flush and conflict check. Existing containers are not retargeted; recreate them after a binding-mode change. The dev.porto.share-mode=bind label opts a container back into ordinary bindings. Paused, disconnected, conflicting or replaced-engine sessions fail before a new workload is created rather than falling back to an empty or stale copy.

Both endpoints can change files. Atomic renames, staging and notifications use the maintained tool's implementation. Ignore patterns and VCS exclusions stay local. Portable permissions synchronize executable bits but not host UID/GID, ACLs or every platform-specific mode. Relative contained symlinks are supported; unsafe links and case collisions are reported. Conflicts retain both versions; inspect the host and guest copies and resolve them explicitly. Neither side automatically wins a destructive conflict. A stopped engine disconnects its session; reconnect uses the same ownership record and pinned guest host key, not a replacement guest. Active synchronized sessions prevent automatic engine suspension until their synchronization is paused.

SSH configuration, verified host keys and the Mutagen daemon are private to Porto. Global SSH configuration and unrelated Mutagen sessions are not changed. The pinned key is recorded for the loopback endpoint and for Lima's lima-<instance> host-key alias, which Lima 2.3 adds to its SSH configuration. Multiplexing, persistence and agent forwarding are disabled for these private connections.

Desktop runtimes include a source-built 0.18.1-porto.1 CLI and Linux amd64/arm64 agents, compiled with the current Go toolchain and pinned patched dependencies. Upstream 0.18.1 prebuilt executables are not used: their older Go and network dependencies have known vulnerabilities. Source development can prepare the same scoped toolchain without installing it host-wide:

bash scripts/bundle-synchronization-runtime.sh darwin arm64 stage/synchronization-runtime
export PATH="$PWD/stage/synchronization-runtime/bin:$PATH"

Use the host's actual OS/architecture; macOS builds require macOS for native filesystem notifications. Ordinary binding mode does not require this tool.

Reproducing native measurements#

On an Apple Silicon Mac with installed Rosetta and the documented development toolchain, first build the runtime inputs:

bash scripts/bundle-desktop-runtime.sh darwin arm64 stage/runtime-darwin-arm64

The following command explicitly authorizes a disposable VZ acceptance VM. It creates private PORTO_HOME and LIMA_HOME directories, uses two CPUs, 2 GiB RAM and a 20 GiB sparse disk, and mounts only its freshly created synthetic projects directory for the ordinary-bind comparison. No home or real project directory is shared. Only that VM is removed afterward; existing Porto engines are not selected:

PATH="$PWD/stage/runtime-darwin-arm64/bin:$PWD/stage/runtime-darwin-arm64/lima/bin:$PATH" \
  PORTO_TEST_NATIVE_RUNTIME_POLICIES=1 \
  go test ./internal/daemon -run '^TestNativeAppleSiliconRuntimePolicies$' \
    -count=1 -timeout=25m -v

The workload is a synthetic amd64 Go HTTP server built into a scratch image, with a no-cache BuildKit RUN step that executes the original Linux binary. It echoes the SHA-256 of an 819,200-byte initiating binary POST, exercises 12 concurrent wakes, a real WebSocket, manual pause, complete engine shutdown, Rosetta/QEMU policy changes, and a native arm64 build. Sharing uses 10,000 small synthetic files, an actual guest container bind, bidirectional edits and inotify. Additional cases use real Docker Compose dependencies and SIGKILL a separate process running the production ownership controller, HTTP wake route and health scheduler. They verify persisted stop ownership, pause quarantine after manual unpause/re-pause during downtime, an active exec, a canceled initiating body, and a real readiness timeout.

The sharing case stops and starts the guest, edits the host while disconnected, verifies both versions and the same session/root identity on reconnect, and creates case-colliding guest filenames against a case-insensitive host. Neither guest version is discarded. Individual native acceptance areas can be rerun:

PATH="$PWD/stage/runtime-darwin-arm64/bin:$PWD/stage/runtime-darwin-arm64/lima/bin:$PATH" \
  PORTO_TEST_NATIVE_RUNTIME_POLICIES=1 \
  go test ./internal/daemon \
    -run '^TestNative(ResourceSaverLifecycle|SynchronizedShareResilience)$' \
    -count=1 -timeout=30m -v

The separate maintained-tool case covers ignores and retained conflicts:

PORTO_TEST_SYNC_BINARY="$PWD/stage/runtime-darwin-arm64/bin/mutagen" \
  go test ./internal/syncshares \
    -run '^TestMaintainedSynchronizationPreservesLargeSyntheticRepository$' \
    -count=1 -timeout=5m -v

An observed run on an Apple M5 Max, macOS 26.6, Go 1.27.3, Lima 2.2.1, an arm64 VZ guest and 0.18.1-porto.1 synchronization toolchain recorded:

Initial 10,000-file host-to-guest synchronization2.632 s

These are reproducible observations, not latency guarantees or cross-product benchmarks. RSS covers the measured owned process subtree, not every macOS Virtualization.framework service or all guest RAM. CPU uses differences between the native VZ process's cumulative ps time samples, not the VM's configured CPU reservation. This already-quiet fixture did not show a measurable idle CPU decrease, and its small build did not demonstrate automatic post-build RSS reclamation. Complete engine suspension removed the measured process instead. The daemon, host listeners and OS caches remain. The earlier tiny-file synchronization result measures metadata-heavy initialization, not sequential byte throughput.

A separate representative sharing run on the same host used the same original amd64 binary in both modes, 10,000 small files and eight deterministic pseudorandom 8 MiB payloads. Both modes traversed 10,011 files after reconnect and edit checks, read exactly 67,108,864 payload bytes, and produced the same SHA-256. The ordinary bind used VZ's host share; synchronized mode used the verified guest-disk copy:

ModeFirst walk/read/hashSecond trialThird trialEffective MiB/s, first / second / third
Ordinary bind630.309 ms253.167 ms318.846 ms101.538 / 252.798 / 200.724
Synchronized guest copy206.137 ms202.439 ms201.321 ms310.474 / 316.144 / 317.900

This includes metadata traversal and hashing, not just storage transfer. Subsequent trials may use caches; caches are not forcibly dropped on the shared host. Initial synchronization of the larger dataset took 2.901 s and is an additional cost, not hidden inside the per-read comparison. Synchronized mode also uses extra guest storage and synchronization resources, so one read alone does not justify it. These observations do not predict every repository's performance or establish battery savings.

The lifecycle acceptance also measures an otherwise-idle HTTP service with a 100 ms housekeeping timer. One run recorded 36,231,000 ns of task CPU over 15.0696 s (0.240424% of one core) and 39,206,912 bytes of task memory before automatic scale-to-zero. Both Compose members then had no runnable tasks; the timer's process CPU cost and process memory were removed, while the initiating request still recovered the group after process loss. These are container cgroup counters and task-state observations, not a whole-laptop CPU, VM-RAM or battery claim. The earlier bare-server host CPU sample remains below its measurement resolution; automatic post-build RSS reclamation is still not claimed.
